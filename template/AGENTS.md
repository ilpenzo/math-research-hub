# Research hub rules

Every AI session in this folder reads these rules. Claude Code reaches them
through CLAUDE.md and Codex reads this file directly. The owner's current
request governs. Old plans, notes, deadlines and handoffs never authorize new
work on their own.

## Start of every session

1. Read START_HERE.md and pick the project the request is about. If the request
   fits no project, or several, ask the owner.
2. Run `python3 tools/hub.py context --project NAME` and read the files it
   lists. Read only the TOPICS.md row you need. Do not preload whole catalogs,
   archives or old notes.
3. Search before proposing work:
   `python3 tools/hub.py search "phrase" --project NAME`. Add `--archives` to
   include the owner's earlier files and `library/`. Look for corrections and
   failed approaches as well as results. An empty search never shows novelty.

## Honesty about mathematical status

- Keep four questions separate. Is it true? Who checked it, and how much of
  it? Is it new? Does it advance the main goal? A yes to one implies nothing
  about the others.
- Status labels mean exactly what WORKFLOW.md says. Never promote a status
  because helpers agree, because a computation passed, or because an old
  report says "verified". Only the owner's instruction or a recorded,
  independent review of a frozen text can make something `verified`.
- State every hypothesis and the exact category of objects. The project's
  AGENTS.md lists the conventions that must always be explicit.
- A finite computation certifies only the cases it ran. A local model or a
  numerical example refutes a global claim only if it satisfies all of the
  claim's hypotheses.
- Never invent a citation. A theorem recalled from memory is a lead, not
  evidence. Before relying on it, check the exact statement, version, theorem
  number and hypotheses in the primary source (templates/source-check.md).
  If the source is unavailable, say so.
- Label every unproved step, assumption and conjecture. Renaming an unproved
  step does not make a reduction. Preserve unresolved disagreements instead
  of averaging them away.
- Write mathematics in plain text in notes and terminal output; use LaTeX in
  .tex files.

## Where things live

- `projects/NAME/catalog/records.json` and `sources.json` are the canonical
  record of claims and literature. Change them only with
  `python3 tools/hub.py put FILE.json`; never edit the JSON directly.
- `projects/NAME/investigations/DATE-topic/NOTE.md` is the lab notebook for
  one question. Create it with `python3 tools/hub.py new-note "topic"
  --project NAME` and keep using it. Never create a separate handoff,
  summary or continuation file that repeats a NOTE.
- Archives (folders of the owner's earlier work, listed in hub.json) and
  `library/` (PDFs of papers) are read-only. Never modify, move, rename or
  delete anything in them.
- Everything in `indexes/` folders is generated by `hub.py render`. Do not
  edit it by hand; it is navigation, not evidence.

## Research method

Retrieve, state the missing step, test controls, attempt, review
independently, record. Before a substantive investigation, write in its NOTE:
the exact statement; the one missing implication that blocks it; relevant
records, corrections and failed approaches; control examples and which
hypotheses each satisfies; a success criterion and an informative negative
outcome.

- Generate ideas before certifying them. Develop analogies and explicit
  conjectures freely, labelled as conjectural. Then test exact statements
  against controls.
- A failed attempt is data. Record its fingerprint: statement, hypotheses,
  mechanism, earliest failure, and what new input would reopen it. Do not
  retry a recorded failure without a new input that addresses that failure.
  The failure of one mechanism does not close a whole direction.
- For substantive proof work follow PROOF_SWARM.md. The main session is the
  proof conductor and develops the argument itself. Helpers answer one bounded
  question each. An author never reviews its own proof, and reviews are of a
  frozen version.

## Computations

- Keep the exact code, inputs and outputs with `hub.py package` (see
  WORKFLOW.md). Record the command, software versions, domain, whether the
  search was exhaustive, and any random seed. A package is a record, not a
  proof.
- Do not rerun old scripts merely to fill the catalog.

## Timed work

If the owner sets a time budget, record the objective, start and deadline in
UTC in the NOTE, with checkpoints. Use the whole budget unless the owner stops
it, a real blocker appears, or the project's success threshold (in the project
AGENTS.md) is met. Finishing the planned helper jobs is not a reason to stop.
Keep roughly the last quarter of the time for checking and writing up.

## Closing out

At the end of every substantive session:

1. Finish the NOTE's "Result and next step" and "Closeout" sections.
2. Record new or changed results and sources with `hub.py put`. For every
   changed existing entry, run `hub.py impact ID` and review what it lists,
   then run a topic search too, since the recorded graph is incomplete.
   Update affected older entries (strengthened, qualified, corrected,
   superseded, or unchanged with a reason), not only new ones.
3. Update the project's TOPICS.md row and add a dated CHANGELOG.md entry
   naming the IDs that changed.
4. Run `python3 tools/hub.py check --project NAME` and
   `python3 tools/hub.py render --project NAME`. A passing check means the
   catalog is consistent; it says nothing about whether a proof is correct.
5. If this folder is a git repository, make a local commit describing the
   change. Never add a remote or push without the owner's instruction.

A new session must be able to tell what changed from the NOTE, the CHANGELOG
and the catalog alone, without the conversation.

## Only on the owner's explicit instruction

Posting, submitting, emailing or otherwise contacting anyone; uploading hub
content anywhere other than the AI service in use; deleting or overwriting
evidence; changing these rules; installing software; pushing to a remote.
Papers and preprints follow the math-paper-writing skill.

## Several sessions at once

Claude and Codex sessions may work here at the same time. Re-read a shared
document just before editing it and never overwrite another session's
changes. `hub.py put` refuses an update based on an outdated read; re-read
with `hub.py show ID` and merge instead of forcing it.
